# v0.11.2 — Split chats, spare-model display, AI role proposals

## Fixed: the status strip repeated in every split chat

`composer.top` renders without a per-composer owner, and the strip always describes the focused chat, so a window with several chats split side by side showed the same strip under every composer. The strip now appears only where the focused chat is shown: its tile, or the primary pane. A tile shows the strip only when it holds the focused chat. The primary pane shows it only with positive identity: the host's focused runtime id equals the primary's runtime id (`host.state.activeSessionId`); a missing tile node is not proof, because a focused tile can be parked and unmounted behind another tab. When the focused chat is also open in a tile, the primary hides, so a chat open in both shows its strip in the tile only. A missing strip is preferred over another chat's strip. Every mounted strip re-checks when another chat surface mounts or unmounts, so a tile that mounts after an asynchronous runtime bind takes the strip without any id change. Popped-out composers are resolved through their owner surface. This reads the host's `data-composer-target` / `data-floating-composer-target` / `data-composer-owner` markup (a compatibility layer, not an SDK API); unknown markup shows the strip as before.

## Added: which model ran after a spare-model switch

The roster records the model/provider transitions of the child's API requests, in order (A → B → A stays visible; bounded to the first and the latest three, shown with `…` when cut). These are request attempts, not confirmed replies. A change is usually Hermes' spare-model handling, but a provider can also substitute a model, so it is shown as an observed change, and the first observed pair is not claimed to be the routed model.

- `실행: <current> (API 호출 기준 · 모델 변경 관찰: <first> → <next> …)`; the line and chip mark it `모델 변경 관찰` / `(모델 변경)`.
- Model and provider are now always recorded as one pair per call; an invalid provider no longer leaves the previous provider next to a new model.

## Fixed: "AI로 역할 제안" was unavailable

The proposal preflight admitted only built-in providers, so a profile whose main model runs through a user-installed provider was refused with `payer_unavailable` (and the dialog showed a generic message). It now also admits the owner's main model on a provider the user installed under its own name that Hermes runs as an external process (`auth_type: external_process`, `base_url` either empty or `process://<provider>`). That is the route every chat of that profile already uses. The dialog says so.

Admission also requires the endpoint Hermes would actually use (environment override or registry value) to be `process://<provider>` with a resolvable local executable. The executable and its ordered effective arguments are bound (hashed) into the route digest, so a change after review is `payer_changed` before dispatch.

Still refused: user plugins that claim any reserved name (static auth rows, every bundled provider plugin and its aliases, the auxiliary router's keywords such as `moa`/`auto`/`custom`), endpoint or key overrides, TCP/HTTP endpoints, other auth types, and user providers in the fallback chain. For every route (primary and each fallback, built-in or not) a same-name `providers:` or `custom_providers` entry, or a malformed shape of either, now refuses the proposal, because Hermes resolves that entry before the registry client. For every payer, a user plugin claiming any reserved name or alias (including `auto`, where a no-task call starts) refuses the proposal.

Known limitation (also in earlier versions): the preflight does not read credential-pool entries (it never reads `auth.json`), so an endpoint stored in a pool row for a built-in provider is not reflected in the disclosure. Proposals are written in the main language of the supplied profile material. `payer_unavailable` now has its own message.
