# v0.16.0: Advisor slot and `ask_advisor`

## New: consult a stronger model without handing off the work

The working agent can now ask one question at a decision point and get the answer in the same tool call. A delegated child runs the task instead of the agent; the advisor only advises. The design follows Claude's advisor tool, where an executor model consults a stronger one when it is stuck.

- New built-in task slot `advise` (label **조언**, Heavy tier), appended after `computer-use`. Its model is set on the settings page like any slot; never set, it follows the Heavy tier as every slot does.
- New tool `ask_advisor(question, context)` in the `model_router` toolset:
  - `question` (1–4,000 characters) and optional `context` (up to 24,000). The advisor sees no conversation, so context carries the decision, the options tried, the evidence and the relevant paths or excerpts.
  - The child's goal is fixed text with a per-call marker (`Advisor consultation <nonce>.`); the question and context go into the task context. Questions with `{user_id}`, `<my-button>` or similar tokens therefore pass the host's batch template-marker check, which inspects goals only.
  - It dispatches one native `delegate_task` child on the `advise` purpose with `background=False` and waits for it. Top-level model-facing `delegate_task` always runs in the background, so the tool calls the native function directly. It calls it through `hermes_cli.middleware.run_tool_execution_middleware`, so every registered tool-execution middleware sees the call as it would see the model's own `delegate_task`. This includes this plugin's runtime watchdog and Fast inheritance.
  - Fixed per call: total runtime 300 seconds (cooperative, so a call can block somewhat longer), and an output schema with `recommendation` and `confidence` (`low`/`medium`/`high`) required and `reasons`/`risks` optional.
  - Returns `ok` / `failed` with `advice` (the child's final text), `schema_valid`, `model`, `route`, `duration_seconds`; `skipped` when the slot runs on the asking agent's own provider and model; `refused` with a code otherwise (`depth_limit` when a delegated child at the depth limit asks). It never raises.
- The `advise` purpose is refused through ordinary `delegate_task`. It stays in the purpose enum because the host rejects values outside it. The route opens only for the exact goal of the in-flight `ask_advisor` call in the same execution context, asked by the same active parent session (not from inside the advisor child).

## Read-only guard

- `subagent_start`: a child whose goal and parent session equal the in-flight call's is bound by its native session id and subagent id. Any child whose goal starts with the advisor marker is bound too, with or without a call record (a reloaded plugin, a rebuilt or continued child); binding more only blocks more.
- `pre_tool_call`: a bound session may call only `read_file`, `search_files`, `web_search`, `web_extract`, `skill_view`, `skills_list` and `vision_analyze`. Everything else is blocked with a message, including terminal, code execution, file writes and patches, browser, delegation and MCP tools. The host unwraps the deferred tool bridge before the hook, so the underlying tool of a `tool_call` is judged by the same allow-list. A call is bound by its session id or by its task id (a child's task id is its subagent id and does not rotate). `delegate_task(action='continue')` of a bound subagent is blocked from any session, including with a padded id.
- `post_compaction`: a bound session's new id is bound too.
- The guard blocks on its own internal errors regardless of how the host treats a hook that raises.
- Bindings are kept per profile in a process-wide store outside the plugin's modules, so an in-process plugin reload (install, enable, update, `plugins.auto_apply`, gateway reload) keeps every binding. A dead session id only ever blocks more.
- If a matching child started without both ids, more than one started, or a result came back with no bound start, the call discards the answer and returns `guard_unbound`.
- The tool is offered (`check_fn`) only after all three hooks registered and while the profile's task routing is enabled. It refuses unless the session delegates through `model-router` or `model-router-auto` and the caller is the active parent (`session_id` equal to the bound parent's).

## Stored spare-model blocks

Per-slot continuation blocks (schema 2) saved before this release name six slots. That exact key set stays valid in both the settings validator and the dispatch validator, with `advise` read as off (`slots.LEGACY_SLOT_SETS`, `slots.complete_slot_keys`). Every other incomplete or extra key set is still refused. Patching such a block writes all seven slots, keeping every stored entry and its consent byte-for-byte.

## Upgrade order

`slots.py` changed, so the existing installed-package check (`slot_capabilities.blocking_profiles`) blocks slot saves until every profile runs this release. Update every profile, restart every Hermes process, then save. A Desktop page from this release talking to an older backend sees no `advise` declaration and hides the slot cards (fail closed) until that profile is updated. Existing sessions keep their pinned tool list; `ask_advisor` and the new enum value appear in new sessions.

## Policy

The bundled skill gains **Asking the advisor**: use it only where judgment is the bottleneck, not for routine steps or to get work done, and never in place of a required Heavy or independent review. The compat skill, the `coding_route` description and `docs/wiki/direct-main-default.md` carry the same rule.

## Limits

- The advisor child is native and fresh: it does not see the conversation and inherits the parent's toolsets; the guard, not the toolset, makes it read-only. Reading is unrestricted, so it can read any file the parent could.
- The execution strip's live roster is fed by `pre_tool_call` for `delegate_task`; the synchronous call bypasses that hook, so the advisor child may appear only through `subagent_start`/stored route reports. Not verified in the Desktop UI.
- `ask_advisor` blocks the asking agent's turn for up to the 300-second limit. It is not exempt from the host's generic tool deadline (default 420 s); if `timeouts.tools.sequential_call` or `concurrent_batch` is set below about 300 s the call reports `tool_timeout` while the child keeps running, still bound.
- The host ignores a caller-supplied iteration budget; the child uses `delegation.max_iterations`. Runtime is the only per-call bound.
- Only agents with delegation depth budget can ask: at the default `delegation.max_spawn_depth: 1` a delegated child gets `depth_limit`.
- With `delegation.worktree_isolation` the advisor child reads a fresh worktree off `HEAD`, not the asker's uncommitted changes; pass excerpts or absolute paths. With `delegation.auto_resume` a rate-limited advisor child can be resumed in the background without the 300-second watchdog; it stays read-only in-process.
- A forced plugin reload during a call also closes the runtime watchdog, so that in-flight advisor child loses its 300-second stop (as for any routed delegation); it stays read-only and the asker waits until the child ends or the host's tool deadline fires.
- Not covered: the moment between unloading and re-registering the plugin's hooks during a reload, and a disabled plugin (no hooks run at all). A restarted process re-resolves a continued advisor child's route, which refuses `advise`.
- Verified offline only, on the host's own per-home plugin manager (real plugin load and forced reload, real `AIAgent` children, real middleware, hooks and pre-tool call site, stubbed model turn): single, repeated, parallel and template-token questions, and reloads during and after a call. No provider response was exercised.
