# v0.13.0: Spare models for compression and title generation, one card layout, no delegation-model editing

This release changes the Desktop settings page (Settings → Plugins → 모델 및 라우팅) and adds one narrow, config-only write path to the service. It changes no Hermes core code. Stored values are not migrated or rewritten.

## What moved

The **모델** section is now one uniform card grid:

- a **대화** group with three cards: **기본 대화**, **대화 압축**, **제목 생성**
- a **작업 슬롯** group, headed by **작업을 맡기는 방식**, followed by the six slot cards **설계**, **코드 · 복잡**, **코드 · 간단**, **검증 · 간단**, **검증 · 복잡**, **컴퓨터 유즈**
- after those: **작업 분담 다시 켜기** (only when needed), the section's target list and **one** save button.

Every card uses the same component (`ModelCard`) and has the same four parts in the same order:

1. title and one-line description
2. model: a role's model, reasoning level and **ID 직접 입력**; for a slot, **모델 기준** (`기본 대화 모델과 같게` or `직접 지정`), and the model, reasoning level and **ID 직접 입력** when it is custom
3. short notes
4. **이 모델을 쓸 수 없을 때** plus the spare-model list. Each card uses the same `SpareChainEditor`: at most 5 rows, **위로** / **아래로** / **이 예비 모델 삭제**, and **예비 모델 추가**.

Both groups use the existing responsive grid: two columns when the page is wide, one column when it is narrow. Element IDs used by tests and other code are unchanged (`model-<role>-*`, `native-chain-<i>-*`, `slot-<id>-*`, `slot-<id>-spare-*`). Cards now also have IDs `model-card-<role>` and `slot-<id>`. Slot-specific notes remain in compact form: the same-model verification note, the per-mode spare note and the auto-mode explanation.

## Removed

- **The 작업 위임 card.** The page no longer edits or sends `delegation.model`, `delegation.provider` or `delegation.reasoning_effort`. This applies to every page save: the model-section save, the whole-page save, re-enable and time-limit saves. Page requests omit the `delegation` role from `models`. The service still accepts the four-role shape from older clients. For a request without `delegation`, the store keeps each target's canonical delegation route exactly (legacy Light and slot routing read it). Only a profile without a stored entry gets the route Hermes resolves. The target's own delegation settings, resolved over its new main model, are used only to verify the apply. None of the delegation keys is written, and the per-key config compare-and-set still covers them. Stored values are unchanged. To change the delegation model, use Hermes' own settings (`hermes config set delegation.model …` or the Hermes model settings).
- **The slot model basis `작업 위임 모델과 같게`.** You can no longer choose it. A slot already following the delegation model, including a never-saved Light-tier slot that resolves through the tier's `delegation` link, is shown as the disabled current value `작업 위임 모델(<model>)과 같게 · 이전 설정`. The page never switches it silently. You can explicitly pick `기본 대화 모델과 같게` or `직접 지정`. **저장된 설정으로 되돌리기** restores the stored value. This follows the retired `default` delegation method in v0.12.0, including target-copy protection. While any slot in the draft still follows the delegation model, the slot models go to the loaded profile only. A copy also never overwrites a slot that a receiving profile has explicitly stored as following the delegation model (`slots.stored`). The page skips that target's slot models, because the slot map is copied as a whole. A never-saved slot that is only shown through its tier's default link is not such a setting, so fresh profiles receive the copy. The service keeps any such stored slot of a non-source routing target exactly, even for older clients. Skipped targets appear in the target list and summary as keeping their own slot models, and they still receive everything else. If the copy intent of a hand-picked list leaves no target that can take the slot models, the save still proceeds without them. An actual slot edit that no selected target can take blocks the save. The message names the receiving profiles' stored setting, or the loaded profile's setting when that is the cause. The server is unchanged: legacy Heavy/Light routing roles and stored slots that follow `delegation` still resolve exactly as before.
- A profile still stored on the legacy `default` delegation method shows no delegation-model card. Its note explains that Hermes keeps using `delegation.model` and that this value can be changed in Hermes' settings.

## Added: compression and title-generation spare models

Hermes has a native per-task spare chain, `auxiliary.<task>.fallback_chain`. The **대화 압축** and **제목 생성** cards now edit it for the built-in `compression` and `title_generation` tasks.

Runtime behaviour, shown in short notes on the cards:

- Hermes uses the chain when the task's model hits a rate limit, a connectivity failure or a payment/quota failure.
- An entry is skipped when it uses the same backend as the failed route (`_failed_backend_skip`). A provider-wide failure, such as an exhausted subscription quota, skips every spare from that provider. A model-scoped failure still lets other models from that provider run. **To cover a provider-wide outage, include a spare from another provider.**
- If every entry fails, Hermes can try the main conversation model as a last resort. It does not always do so; for example, it does not after an authentication failure on an explicitly configured provider.
- For compression, entries below the minimum context window are skipped.

### Off and kept chains

Hermes has no enabled flag for this chain. **Off** therefore means no spare models in the Hermes config:

- If the key is absent (or `null`) and the page saves Off, nothing is written. **An absent key stays absent.**
- If a stored chain is switched Off and saved, the page writes `[]`, which Hermes treats as no chain.
- A chain the user did not edit is never sent, unless the section's target list was hand-picked while that chain is On. In that case it is copied like the conversation spare models. Off is copied only as an explicit edit, so a hand-picked target list never clears another profile's chain by itself.
- Only an explicit Off clears a chain. An On draft without a valid row, for example after the last row was deleted, is an error on both save paths (the model-section save and the whole-page save) and is never sent as `[]`.
- The page never stores a disabled chain in Hermes config. While Off, the rows stay only in the page draft. Turning the chain back On before saving restores them. The note tells you whether saving Off will delete a stored list.

### Service write path

The existing `/fallback-preview` plan accepts one new per-update field:

```json
{"profile": "p1", "auxiliary_fallback": {"compression": [{"provider": "deepseek", "model": "flash"}], "title": []}}
```

It also accepts a new confirmation scope, `auxiliary`. The whole-page save sends the same field in its combined `/preview` (`fallback_updates`). Safety properties:

- **Exact keys only.** Writes are limited to `auxiliary.compression.fallback_chain` and `auxiliary.title_generation.fallback_chain`, and only for profiles listed in `updates`. A task missing from the mapping is not touched. The writer allow-list (`config_writer.ALLOWED_KEYS`) contains exactly these two new keys. Nothing is stored in the plugin store, so the store schema read by every installed package is unchanged.
- **Strict validation, matching the conversation chain and the page.** Entries contain `provider` and `model` only; `base_url`, `api_key` and secrets are refused. Provider and model tokens follow the conversation spare-model rules; `tests/fixtures/fallback_token_cases.json` is shared by the service and page tests. A chain has at most 5 entries, with no case-folded duplicates. A spare must differ from the task's own primary model, resolved as Hermes resolves `auxiliary.<task>` (`_resolve_task_provider_model`):
  - `model: auto` (any case) counts as unset.
  - With no provider (or `auto`) and no model, the task uses the main model.
  - With a concrete provider and a model, the task uses exactly that.
  - With a concrete provider and no model, the task uses that provider's catalog default. With `auto` and a model, the route goes through auto-detection. Neither can be established here, so for these two cases **only the equality check is skipped**. Hermes tolerates such a spare: a spare on the failed backend is skipped. The chain stays editable.
  - For a model target in the same plan, the check uses that plan's approved models.
  - The page and service share `tests/fixtures/auxiliary_primary_cases.json`.
- **Read-only cases.** A key is read-only when it has a managed (administrator) overlay, an env expression, an entry with extra fields such as `base_url`, a provider-only entry, malformed content or an unverifiable effective read.
  - **Provider-only entries** (Hermes runs them on that provider's default model) are shown with their provider and an empty model. They are never dropped, so an active chain never appears Off. The card says that this editor cannot represent the entry.
  - **Env expressions** (`${...}` in the stored or resolved chain): neither the stored nor the expanded provider/model is ever returned. Each entry is reported as `[env]`, and `env_masked: true` is set. In those cases the status reports `editable: false`, and the preview refuses the update. Built-in tasks cannot be re-registered by a plugin, so plugin `inherit_from` does not apply to these two blocks.
- **Compare-and-set.** The page freezes `expected.auxiliary_fallback` (stored and effective chain) for **each task it writes** for every profile it writes. The service requires and compares only those tasks, so a sibling task changed elsewhere never blocks the save. Older bodies that freeze both tasks still work. A mismatch is a structured `ExternalChange` (`field: auxiliary_fallback.<task>`) through `cli_error_payload`, and nothing is written.
- **Per-task snapshot.** Each task's status, editability, warnings and plan baseline come from a snapshot of that task's own key, read once.
  - The plan records one effective-config digest and one managed-provenance digest per written key, from the same read that decided its editability.
  - Readback after apply covers only the written keys.
  - A sibling task's env expression, malformed value or overlay, or its change between preview and apply, therefore never locks or refuses the other task. Each card names that task's own read-only cause: environment variable, administrator setting, advanced entry, unrepresentable format, or unverifiable.
- **Primary-route binding.** The keys the task's primary was resolved from (`auxiliary.<task>.provider`/`.model` and `model.provider`/`model.default`) are part of the plan's per-key compare-and-set. A change before apply refuses the apply. The plan also records the raw digest of each written key (checked again immediately before that write), the key-scoped effective snapshot digest (checked at preview end and apply start) and the managed provenance digest (checked before each write).
- **Readback.** After writing, the stored chain and the chain Hermes resolves must both equal the approved chain. Otherwise the apply reports `partial`, and the page does not retry.
- **Cost confirmation.** This uses the same semantics as the conversation spare models. Clicking Save is consent, and the card shows one short cost line. Every write that sets a non-empty chain requires an `auxiliary` confirmation with `allow_additional_cost: true`. Turning the chain off does not.
- **Older clients are unaffected.** Bodies without `auxiliary_fallback` behave exactly as before. An `expected` row without the new field is simply not compared.

### Status additions

Each profile row has `auxiliary_fallbacks.compression` and `auxiliary_fallbacks.title`:

```json
{"schema": 1, "key": "auxiliary.compression.fallback_chain", "editable": true, "present": false,
 "chain": [], "actual_chain": [], "drift": false, "managed_overlay": false, "env_masked": false,
 "primary": {"provider": "openai-codex", "model": "gpt-6-astra"}, "warnings": []}
```

`chain` is the profile's stored chain, and `actual_chain` is the chain Hermes resolves. `drift` is true when they differ, and the card then shows the actual chain. `present` reports whether the key exists in the profile config. `primary` is the task's own model as resolved above, or `null` when it cannot be established here.

## How the model section saves now

The single model-section save still uses the narrowest existing steps, in order:

1. `/delegation-preview`: the delegation method and slot spare models
2. `/preview` with `save_scope: 'models'` (or `'routing'`, or unscoped when both changed): role models and slot models
3. `/fallback-preview`: conversation spare models **and** compression/title spare models, in one body

A spare-model-only edit, including a compression- or title-only edit, sends step 3 alone. It never starts the store-wide routing pass. When step 2 changes a target's main or task model, step 3 is checked again after step 2 applies, against the new models. Targets that cannot take a part are named as skipped and still receive the rest. Per-target summaries are derived from the request bodies, and partial results are reported per step without automatic retry. Automatic reload still happens only when the applied request bodies carried every unsaved edit. The compression and title chains are tracked as separate dirty parts, and copying through a hand-picked target list is tracked as another.

## Safety (unchanged)

The following v0.12.x guarantees still hold:

- per-profile `expected` compare-and-set
- the store digest check at apply start and immediately before `os.replace`
- preservation of untargeted entries
- absent keys staying absent
- dirty tracking against the frozen baseline
- coverage computed from actually applied request bodies
- auto-reload only when every dirty edit was submitted
- staged transfer
- save fences and generation tokens
- dispatch-time drift rechecks using refs
- structured `ExternalChange` errors

An external change to a compression or title chain blocks only the model-section save that would write that chain. The whole-page save is still blocked by any live drift.
