# v0.15.1: Each composer shows its own chat's status line

## Fixed: the primary pane lost its status line while a split tile held focus

Reported case: a window whose primary pane showed conversation A and whose split tile showed conversation B. Clicking A's composer moved keyboard focus into A, but the host kept reporting B as the focused chat (`focusedStoredSessionId`/`focusedSessionId` stayed on B). A strip shows only when its composer's session equals the focused chat, so A's composer never showed a strip, and the data the plugin read was B's. That host focus projection is a Hermes Desktop defect outside this plugin.

What changed:

- `composerStripMode(session, focusedStoredId, focusedRuntimeId, primaryRuntimeId)` decides what each composer's strip reads:
  - `focused`: its stored id equals the focused chat (unchanged).
  - `primary`: its runtime id equals `host.state.activeSessionId` while another chat, with a known runtime, holds focus.
  - hidden: an unfocused tile, a draft or an unknown session. A bare stored-id string from the hook can only match `focused`; it is never treated as a runtime id.
- **Owner proof.** While a tile holds focus the host publishes no owner for the primary, and the active socket is not proof of one: all-profiles navigation dials the owning backend without moving the active profile, and eviction or cold start can leave a different active route. So a `primary` strip reads only under an owner proof.
  - The focused primary composer reports its own runtime-to-stored binding (`notePrimary`). The observer accepts it only if the live host state agrees (`activeSessionId` = `focusedSessionId` = runtime, `focusedStoredSessionId` = stored). It takes the owner only from the host's `focusedSessionOwner` (`executionPrimaryProof`). The ambient connection or profile never supplies it.
  - The observer drops the proof when `activeSessionId` changes, the activation epoch changes, the gateway instance is replaced, or the socket state resets. A primary that is still focused records it again after any reset the observer sees (an `onState` event, an atom change or `notePrimary` itself), including one focused while the socket was still connecting. An activation-epoch bump with no such signal is noticed on the next read; if a tile takes focus first, the primary line stays hidden until the primary is focused again.
  - If the host stops resolving the owner while this exact primary is focused, the proof is withdrawn too.
  - `executionPrimaryScope` then yields `{proven connection, proven profile, activeSessionId}`. Reads still require that pair to equal the live connection and profile, on a local, open, canonical socket.
- Without a proof the primary strip stays hidden and issues no reads, so no false "읽을 수 없습니다" line appears. This covers a primary opened while a tile was focused, and the time after a plugin reload until the primary is focused again.
- While the primary itself is focused, the host's focused-owner projection governs as before, and an unresolved owner still fails closed.
- Job controls on a `primary` strip are replaced by one note per strip (`작업 제어는 이 대화를 포커스하면 사용할 수 있습니다.`), because their fence follows the focused chat. The full-profile job guide is not mounted there.
- `plugin.js` `version` is now 0.15.1, matching `plugin.yaml`.
- Hosts without `useComposerSession` keep the previous always-show behaviour with the focused scope.

## Limits

- The primary strip appears only after the host has reported that conversation as the focused primary at least once since the plugin loaded, the primary changed conversation, or the connection or activation last reset while a tile held focus. Selecting it in the sidebar fronts the main pane and does this. In the reported window the host never did so from composer clicks alone.
- An unfocused split tile shows no strip, unless its composer reports the primary's runtime id (its own conversation, shown under the primary's proof). The host publishes no owner for any other tile.
- If the host gives a tile the primary's runtime id (the same conversation in both) while a third chat is focused, both composers show that conversation's line. This depends on host runtime binding and was not verified.
- A change of the primary's conversation while a tile is focused re-reads every strip, so the focused tile's line briefly reloads, as it already did on any focus change.
- The host focus defect itself is unchanged. Other host readouts that follow `focusedStoredSessionId` still describe the tile.

## Tests

- New `tests/test_composer_strip_split.mjs`, with real contributed strips, real React and Query, and an inert host:
  - After one primary focus, each composer shows its own chat, and the primary-mode job note replaces the buttons.
  - The documented flow works: opened under tile focus, selected once in the sidebar, then the tile again.
  - A late-resolving owner is recorded, and a retracted owner withdraws the proof.
  - A transport reset, or a primary first focused while connecting, re-records the proof.
  - One job note and no job guide on a primary strip, and `plugin.js` `version` matches `plugin.yaml`.
  - No note without a gateway job line, and a stored id that resolves after mount still records the proof.
  - The gate removes its revision listener on unmount, and a re-note queued just before unmount records nothing.
  - Primary navigation hides the primary line.
  - Without a proof the primary is hidden and never read.
  - A primary proven to another profile is never read through the active socket.
- Observer:
  - Proof required, and ambient labels never admitted.
  - Refusals carry the proven labels: other profile, remote connection, unresolved owner.
  - Proof dropped on navigation A-B-A, epoch change, socket reset and instance replacement.
  - An in-flight primary read is invalidated by a primary A-B-A and by focus moves.
  - Primary focused with an unresolved owner still fails closed.
  - A note while another chat is focused never withdraws the proof.
  - `notePrimary` settles a silent transport change before answering.
- Unit tests for `composerStripMode`, `executionPrimaryProof` and `executionPrimaryScope`. Gate tests cover the primary, tile, unfocused-tile, draft and bare-string cases.
- Mutation check: these mutants are each caught:
  - ignoring `scopeMode` or dropping the prop;
  - removing the `activeSessionId` listener or the primary key from the observer signature;
  - keeping the proof across navigation or after an owner retraction;
  - using the ambient owner;
  - empty gate deps, no revision listener, a listener left after unmount, or no `live` guard;
  - mounting the job guide in primary mode;
  - a note per row;
  - a stale `version`;
  - no binding-live condition on retraction;
  - no settle before `notePrimary` answers;
  - gate deps reduced to the observer;
  - no revision listener;
  - a note without a gateway job line.

  `ownerKey` and `focusedStored` in the gate deps overlap with `mode` and the revision listener by design, so dropping either alone, or `stored` alone (covered by `mode`), is an equivalent mutant.
- Full Node and Python suites: same failures by name as origin/main (8 Node `actual SDK …` tests; 164 Python tests in this environment), none new.
- The gate re-notes on observer revisions through a deferred listener, not a render subscription, so it never updates inside another component's render. A dev-only React warning naming `ExecutionPanel` (a render-phase `eligible` check, an `onState` reset or disposal can bump the shared revision while a strip renders) predates this release and is unchanged.
