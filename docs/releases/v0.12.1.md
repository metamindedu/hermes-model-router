# v0.12.1 — Conversation spare models inside 대화 모델, saved with the model section

This release changes only the Desktop settings page (Settings → Plugins → 모델 및 라우팅). The service, the CLI bridge and the request shapes are unchanged; stored values are neither migrated nor rewritten.

## What moved

The conversation spare models (native `fallback_providers`) no longer have their own card. They sit inside **대화 모델**, directly under the main conversation model's picker, in the same pattern as a task slot's spare models:

- **이 모델을 쓸 수 없을 때**: `다른 모델로 전환하지 않음` (off, `enabled: false`) or `예비 모델로 이어가기` (custom, `enabled: true`). Choosing custom with an empty list adds one row to fill in.
- the spare-model rows (at most 5), each with **위로** / **아래로** / **이 예비 모델 삭제**, and **예비 모델 추가**.
- Switching off keeps the stored chain (it is shown as kept, not deleted); a row that was added and left completely blank is dropped. Switching back on shows the kept chain again.

The validation is unchanged: at most five entries, no duplicate provider/model, no spare equal to the main model a target will have, and turning it on needs at least one entry.

The copy is shorter: the three status lines (저장 설정 / 편집 초안 / 실제 적용 경로), the long introduction and the recovery note are gone. The page shows a warning only when the chain actually applied differs from the stored one (`drift`, with the applied chain) and lists the status warnings. The managed-elsewhere, read-only and unsupported notes remain when they apply, and the cost note is one short line shown while the spare models are on.

## How it is saved now

The separate card's target list and its **대화 예비 모델 저장** button are removed from the page. The existing narrow `/fallback-preview` endpoint stays. The model section's save (**선택한 N개 프로필에 모델 설정 저장**) now saves the conversation spare models too, to the model section's targets:

- They are written when the draft differs from the value frozen when the profile was loaded, or when the section's target list was picked by hand (the section's copy intent, which already copies the role models, the slot models and the delegation method). An untouched page never sends them.
- The model section saves only the steps that are needed, in order: the delegation method and slot spare models via `/delegation-preview`, role and slot models via the existing `/preview` store path, then conversation spare models via `/fallback-preview`. A conversation spare-model-only edit sends no store or delegation preview. It never starts the routing pass or needs the resolved models of an untargeted profile.
- The conversation spare-model step uses the store revision from the preceding store apply and keeps the original per-profile `expected.native_fallback` and native cost confirmations. When the model step changes a target's main model, the fallback preview validates against the new main model after the model step applies; it stays the authoritative check. Before the first write, the page already refuses what that preview would refuse deterministically, with the service's rules: literal provider/model tokens (no surrounding spaces, the service's character sets, never `KEEP`), no duplicates and no spare equal to the main model each receiving target will have (its projected main model for a model target, its stored main model otherwise, never the actual one, as the service compares), both compared with provider and model case-folded. If a step fails, the page distinguishes saved steps, failed or unconfirmed steps, and steps that never started; a refusal because a value changed elsewhere names only the step it stopped. It does not retry or reload over unsaved edits.
- A target that cannot take the conversation spare models (not readable, read-only, or the backend's fallback capabilities are not confirmed) is named in the target list and in the summary as skipped. It still receives the models (and the delegation method when eligible), and the save does not fail because of it. A changed value that the loaded profile itself cannot take, or that no selected target can take, blocks the save by name instead of being dropped. As with the former card, nothing is written while the loaded profile's own conversation spare models are not editable here, also when a refresh makes them read-only mid-edit and the loaded profile is not a target; a save callback kept from an earlier render rechecks this against the newest status before it sends anything.
- The per-profile summary is built from the request bodies and distinguishes role models, slot models, the delegation method, slot spare models and conversation spare models. It names skipped targets even when fallback capabilities are absent.
- The whole-page save (**기본 모델·시간·기타 설정 함께 저장**) still sends the spare models once, in its single unscoped combined request. As in v0.12.0, the whole-page routing pass may write `skills.disabled` for a routing-off profile even if that profile is not a model or fallback target. The existing slot-model store path also retains its routing pass.

## Removed

- The conversation spare-model presets (`NATIVE_FALLBACK_PRESETS`, `applyNativeFallbackPresetDraft`). Nothing else used them. The routed-job presets used by older stored values are unchanged.

## Added

- Priority reordering for both spare-model lists: the conversation chain (`native-chain-<i>-up` / `-down`) and every task slot's chain (`slot-<id>-spare-up-<i>` / `slot-<id>-spare-down-<i>`). The first entry cannot move up and the last cannot move down; reordering only edits the draft.

## Safety (unchanged)

Every existing fence still applies: per-profile `expected` compare-and-set and the store digest check at apply; the automatic native cost-consent confirmations (the explicit save is the consent, as with the old card); unsaved edits compared with the frozen baseline (the conversation spare models are tracked as their own part, and the section's copy of them as another); automatic reload only when the request bodies actually applied carried every unsaved edit; staged transfer for large bodies; generation tokens and the native save fence. An external change to a conversation spare-model value blocks a save that would overwrite it. A routing-only drift does not stop a standalone conversation spare-model save, which does not write routing.

## Copy behaviour

A hand-picked model-section target list now also copies the loaded profile's conversation spare models (including an off value with its kept chain) to every selected target that can take them, in the same way it already copies the slot spare models. Previously a model copy left the other profiles' conversation spare models alone.
