# v0.13.2: Completed profile delegations show the model they ran on

This is a patch release. It changes no Hermes core code, adds no write path to any database, and does not migrate or rewrite stored values. Status: candidate — the bounded read exception below was adopted by the user on 2026-11-20 (recorded in PLAN.md); a final independent delta review returning GO is required before release.

## Fixed: a completed profile delegation showed 모델 보고 없음

**Symptom.** The execution strip above the composer showed a completed native profile delegation (`delegate_task` with `execution: 'profile'`, e.g. profile `claire`) as **모델 보고 없음** / **실행: 아직 API 호출 보고 없음**, while the same line showed **모델 호출 11회 · 토큰 32만**. Real case: session `local-874c7387…`, delegation `deleg_9b8c23bb`, child `sa-0-42a7cfcf`.

**Cause.** A profile-routed child converses under the target profile's home scope, so the origin profile's `pre_api_request`/`post_api_request` hooks never observe the child's API calls and the roster row keeps no model. The dispatch-time tool result carries only ids (`status: 'dispatched'`). The per-task route report — the backend/label/model/provider the child actually ran on, read off the child when its result is assembled — is written to the origin's `async_delegations.result_json` ledger when the child finishes (partial entries land per finished child while the unit runs). After completion the live `subagent.list` roster drops the child, so the desktop's third model source disappears too. Nothing read the stored report, so all three model sources (API hooks → route report → live roster) were empty while replay events still supplied the call/token counters.

**Fix.** A new admitted adapter `model_router/delegation_reports.py` projects the stored route report, and `execution_roster.list()` fills `row.observed` for bound rows that still lack a model from every live source. The desktop is unchanged: its existing route-source path renders the pair labelled **런타임 보고** (e.g. `qwen/qwen4-max:free · nous (런타임 보고)`), and the chip shows `프로필 · claire · qwen/qwen4-max:free · 완료 2분 24초`. The stored report never overwrites the API-hook model (`row.model`) or an inline result's observed report; the desktop source priority is unchanged.

## Fixed: a refused delegate_task request lingered as 실행 중 (phantom row)

**Symptom.** A `delegate_task` call refused as a whole (for example a routing refusal before any dispatch, returning a top-level `{"error": ...}` with no task results) left its roster row in the `requested` state forever. The execution strip counted it as **실행 중** and showed **모델 보고 전 / 아직 API 호출 보고 없음**, although no child ever ran. Real case: this conversation's first review dispatch was refused for a missing `execution` field; hours later the strip still showed it as a running request alongside the completed review.

**Cause.** The roster's `post` hook settled per-task refusals (the `refused` list) and dispatched/inline results, but a whole-call top-level error has no task-index structure, so `_apply` did nothing and the requested row never reached a terminal state. `requested` is in the desktop's active set, so the phantom counted as running indefinitely.

**Fix.** On a top-level error result with no `results`/`refused`/`inline_results` list and no `dispatched` status, the still-unbound requested rows of that exact call are settled to `error` (terminal). The strip then counts them as **오류**, not 실행 중. A row that already dispatched keeps its own evidence — a late top-level error never overwrites it; per-task refusals still ride the `refused` list through `_apply`; an error carrying inline results still processes them. No new read or write path; this is pure in-memory status settling.

**Also closed (cancel/timeout/abandon).** The core sends a cancelled, timed-out or abandoned `delegate_task`'s terminal `post_tool_call` with a plain-text result (no JSON) plus a terminal `status`/`error_type` kwarg. The roster now parses the result safely and uses that terminal failure status (`error`/`interrupted`/`cancelled`/`timeout`) as an auxiliary signal to settle the still-unbound requested rows to the same terminal state. A `completed` hook status never force-settles, and dispatched/bound rows are never touched.

## Changed: composer strip gating uses the public SDK seam (catalog admission)

The catalog review of v0.13.1 (PR 155752) required retiring the private host-markup gate before listing. `ComposerFocusGate` previously read the Desktop app's own markup (`data-chat-surface`, `data-composer-target`, `data-composer-owner`, `data-floating-composer-target`) and attached `pointerup`/`focusin`/`keyup` listeners on `document` to decide which composer shows the strip — fragile across composer refactors.

It now uses the public SDK seam, feature-detected: `DesktopSDK.useComposerSession()` (added to the host SDK in PR 144792) tells a `composer.top` contribution which session its own composer belongs to, and the strip shows only when that `storedSessionId` matches the focused chat (`composerStripVisible`, positive identity match, fail toward hiding). On hosts without the hook — including this install, where the hook is not yet released — it falls back to always showing the strip, exactly the pre-gate behaviour. No host markup is read and no document-level listeners are attached; the `data-chat-surface` helpers and the gate re-check `Set` are removed. The change is dormant where the SDK hook is absent and forward-compatible where it lands.

## The bounded read exception (disclosed contract change)

The roster now reads this origin's own private native database — a bounded exception to the earlier "normal visibility does not recover private native database records" contract, which README.md and SECURITY.md previously stated and which the fence test guarded. The exception is necessary: the core exposes no public hook or event carrying a profile-routed child's model (`subagent_stop` and `subagent.complete` carry no model field), and Hermes core changes are out of scope.

Exact scope:

- **Which rows:** only rows already bound by this origin's delegation hooks — exact delegation unit (primary key) + parent session id + task index, plus the subagent id when both sides name one. Never user-supplied targets.
- **Which fields:** only scalars — entry `status`, `subagent_id`, `task_index`, `route.backend`, `route.label`, `route.model`, `route.provider`, and the entry's reported `model`. No task, goal, result, summary or transcript text; no whole JSON record leaves SQLite; no other profile's home is opened.
- **When:** on `execution.list` reads, only for rows with no model from the live API hooks or an inline result. Newest rows first (cap 32 per read); units that can never produce a report (pruned, or finished without a usable route) are negative-cached (bounded 256) and not re-read; `running` units stay retryable for partial reports.
- **How:** read-only URI, `query_only`, snapshot `BEGIN`, symlink/reparse refusal, home fixed at registration. Bounded: 2 MB result cap, 128-entry cap, duplicate task indexes rejected, a 0.15 s query deadline checked in Python at every lookup (the progress handler alone does not bound lock waits or short statements; under an exclusive ledger lock the wall-clock is the deadline plus a short busy wait, ~0.3 s measured, always outside the hook lock). The first SQLite error (busy/locked included) closes the snapshot so remaining lookups fail fast. All reads happen outside the shared hook lock; adoption re-checks live evidence under the lock.
- **Writes:** the database body is never written. A WAL read may create `-shm`/`-wal` sidecars when no other connection holds the database; in normal operation the core already holds it.
- **Fail closed:** missing database/table, malformed or non-object JSON, stringified `results`, non-integer task indexes, non-terminal entries, oversized/overfull results, parent/unit/task/subagent mismatch — all stay unknown. An unexpected adapter error never empties the roster.

The unadmitted research adapter (`model_router/execution_metadata.py`) and its direct research tests remain excluded from the package and are never imported by the roster. Adoption of this exception is recorded in PLAN.md with the user's explicit decision; the fence test's name/scope is redefined accordingly (unadmitted-adapter import ban vs. the admitted bound-row read).

## Hardening from the independent Heavy review

The first independent final review (delegation `deleg_7e3fd2e7`, Heavy slot; assigned `gpt-6.2-astra · openai-codex`, executed `claude-fable-5-2[1m]` after a spare takeover, 32 API calls) returned **BLOCK**: the fix logic, attribution and privacy scope passed, but the contract/documentation tension above and a measured 3.5–10.6 s shared-lock hold under an exclusively locked database were release blockers, with minor findings on starvation, JSON type strictness, WAL wording and exception isolation. All named issues were repaired in this candidate:

- Ledger reads moved outside the shared hook lock (lookup keys collected under the lock, reads outside, adoption re-checked under the lock).
- First SQLite error closes the snapshot; Python-side deadline check at every lookup; locked-DB regression tests assert fail-fast timing and retryability after unlock.
- Newest-first lookup order + bounded negative cache (no starvation behind dead rows; no per-poll re-open for unresolvable units).
- Path-argument `json_type`/`json_each` forms reject stringified arrays; a `CASE WHEN j.type='object'` guard skips non-object elements without a malformed-JSON abort, and the integer-type guard rejects real/boolean task indexes.
- "Never writes" claims scoped to the database body; WAL sidecar behavior disclosed and tested.
- Route-refresh exceptions isolated so `list()` never returns empty rows because of them.
- Regression tests added for each of the above, plus compaction-alias parent binding and running-unit partial-report retry.

## Known limitations (unchanged or disclosed)

- The stored report is read only when the conversation's roster is read. If the desktop never reads the conversation before the ledger prunes the unit (core retention: 50 terminal units per home, age cap), the row keeps 모델 보고 없음.
- `waiting_to_resume` entries and children finished by automatic resume in a new unit are not adopted into the original row (honest unknown).
- `route.fallback_activated` is not projected: a spare takeover shows the final model without a "모델 변경 관찰" marker on profile rows (the API-hook spare marker is unchanged for model rows).
- Rows whose stop hook never matched can show a model while their status stays 대기; the stored report does not settle status (out of scope).
- `profile_task` (Gateway full-profile job) rows are a separate transport and still show no model; fixing them is separate work.
- The adapter depends on the core's private `async_delegations.result_json` shape; a core schema change silently degrades to unknown (fail closed), never to a wrong model.
- If a refused call's `tool_call_id` is reused to dispatch again in the same session, the settled `error` row keeps its terminal state while only the delegation/subagent ids bind (a pre-existing limitation shared with completed rows; `tool_call_id` reuse is the precondition).
- The composer SDK seam is dormant on hosts without `useComposerSession` (including this install): the strip falls back to always showing under every composer until the host SDK ships the hook, exactly the pre-gate behaviour the catalog review prescribed.
