# v0.10.0 — Native parent return and scoped execution visibility

## Changes

- Adds the opt-in `profile_task prepare` → exact ordinary terminal/helper → public process witness → `start(return_id)` workflow. Preparation reserves an immutable job binding without creating/submitting target work. Native helper completion wakes the original surviving parent, which retrieves the exact visible result through normal `profile_task result`.
- Keeps starts without a return ID on explicit collection. Native `delegate_task` completion remains a separate, unchanged Core-owned route.
- Separates requested identity, runtime evidence and missing/unknown counters in execution views. Bounds observer DTO/query lifetimes and rejects stale owner/scope/generation results; no global cache clearing or private native database recovery is enabled.
- Uses real public middleware correlation, finite pre-launch readiness/result deadlines, exact request/payload retry checks and lifecycle serialization. Unsupported context/channel/filesystem conditions refuse before target effects instead of bypassing the boundary.

## Supported boundary and verified behavior

Automatic return has been exercised with real native Windows CLI/ConPTY/Gateway execution, local NTFS/ASCII paths and synthetic final model HTTP. Verified cases include ordinary automatic return, actual summary continuity, different-parent rejection after normal `/new`, and helper-only cancellation while the original business job still completes. The compression test did not rotate the physical SID; it is not alias-transfer coverage. Helper cancellation is not business cancellation/completion. Each conformance case used one actual inert target session/input and one ordinary business completion, with public/canonical receipts, not private Core SQL or captured authentication frames.

This is **surviving-parent-session lifetime only**, `persist_on_release:false`. Durable true remains refused. No restart/reboot/host-exit recovery, every host/isolation mode, Linux/macOS return path, real provider/account, or same-user OS-sandbox guarantee is added. Existing source-owned read/result and exact stop behavior remain separate from helper delivery. Unknown effects never authorize a replacement target.

## Permissions and installation

Installation does not enable full-profile grants, choose a model/backend, copy credentials, authorize target accounts/tools/memory/costs, force a session reset or run provider tests. Existing OFF, grants, model/fallback policy and tool-scope choices remain unchanged. A compatible supported tool boundary may be needed before an existing conversation sees new parameters.

Normal dependency admission retains both bounded requirements: `PyYAML>=6,<7` and `websockets>=15,<17`. The release excludes the unadmitted `model_router/execution_metadata.py` research adapter and its direct research test file. Remaining visibility tests exercise matching-origin public compaction/stop signals and unknown gaps without importing that adapter; they do not relabel private-schema recovery as public behavior. Earlier research coverage remains in retained development evidence, not the admitted release suite.

Normal local exact-ref installation, default/named profile preparation and explicit disabled preservation were exercised with a self-contained synthetic input artifact. That SHA is not a published release commit or official-catalog pin. Final version/commit tests and live installed-owner/UI readback are separate release checks. Earlier development-suite totals must not be reported as the final excluded-research release count.

## Publication and compatibility

Inherited private-Core import warnings remain explicit compatibility/public-surface debt. No new warning target was introduced by the automatic-return implementation, but successful local admission is not catalog clearance. Public availability and catalog pinning depend on their ordinary source/review/maintainer lifecycle. Automatic new-profile installation remains unavailable when source, SHA and version do not match the catalog; custom/disabled profiles stay manual/preserved.

No Hermes Core modification, credential migration, permission expansion, automatic task replay or shared-owner restart is part of this release.
