# v0.12.0 — Settings page restructure: profile delegation section, conversation spare models in the model section

This release restructures the Desktop settings page (Settings → Plugins → 모델 및 라우팅) and refines the bundled delegation guidance (below). Stored values stay as they were: nothing is migrated or rewritten on install or when the page opens, and a save leaves every part it does not edit exactly as stored, including keys that are absent. Two service requests accept a part being left out (see "Service changes"); bodies from older pages are still accepted unchanged.

## New page structure

1. **불러올 프로필** (unchanged)
2. **모델**
   - 대화 모델 (unchanged)
   - **대화 예비 모델** (moved here; was the "일반 대화 폴백" card in the separate fallback section)
   - 작업 모델: how work is handed off (작업을 맡기는 방식) and the six task slots with their spare models
   - re-enabling task routing, the model section's target list and save button
3. **전문 프로필 위임** (new section)
4. 작업별 실행 시간 제한 (unchanged)
5. 함께 저장 (whole-page save)

## Profile delegation is its own section

The allowed profiles (`profile_routes.profiles`), the per-delegation descriptions including "AI로 역할 제안", the default profile for the profile-only method, and the account-use consent moved out of the model section into **전문 프로필 위임**, with its own target list, summary, errors and save button.

- The section is editable only while the loaded profile's **stored** method uses profiles (`model-router-profiles` or `model-router-auto`). Otherwise it shows a short read-only note with the stored allow-list. Choosing a profile method in the model section is not enough; save it first, then edit the profiles.
- Both sections still go through the same native path: `/delegation-preview`, the fresh-status check before apply, the native save fence and staged bodies for large requests. The batch builder takes a part, and each update leaves out what that part does not edit:
  - the model section's save sends the drafted method, plus the slot spare models only while their slot cards are on screen; without slot cards (for example when choosing a profile method) it is a method-only update. It omits `profile_routes` (with `allow_profile_access: false`), so each target keeps its stored allow-list, descriptions and default byte-for-byte, even one that still names a deleted profile;
  - the profile section's save sends the drafted allow-list, descriptions and consent with each target's stored method, and omits the spare policy. It saves only to profiles whose stored method uses profiles; a target that cannot take it is disabled in the list, skipped by "가능한 프로필 모두", and, if it changes after being ticked, blocks the save by name. A ticked target that disappears from a refreshed status, or only from the fresh status the save reads just before applying, also blocks the save by name and stays listed until it is unticked, and the account-use consent is reset. Nothing is applied in that case.
- The default profile is edited only on a profile-only (`model-router-profiles`) source. Copied from an automatic-mode source, the allow-list keeps each target's stored default unless that profile left the list.
- Account-use consent protects new authority only. It is required to add a profile to the allow-list or to change the default profile to a different profile; it is not required for description-only edits, removing profiles, clearing the default, or saving a block whose stored default is unchanged. The service enforces the same rule.
- The profile section starts with the loaded profile as its only target. Changing that target list resets the account-use consent; the model section's target list no longer does.
- Unsaved edits are compared with the loaded profile's frozen baseline only, never with refreshed status rows or with whether a section is editable at the moment. Each field is tracked on its own: role models, routing roles, slot models, the method, the model-only and automatic spare models, the allow-list, the default profile, the conversation spare models, timeouts, re-enabled routing, and each pending copy from a hand-picked target list.
- Write intent is the same comparison: a save writes a part only when its draft differs from the frozen baseline. A refreshed status is never treated as an edit. If a value the page would write changed elsewhere since it was loaded at the same store revision (models, routing roles or on/off, slot models, conversation spare models), the page names the profile and value that changed (for example the routing on/off of another profile), blocks the saves that would write it, and asks for a reload instead of writing the old value back. This check runs again when a save is dispatched, against the newest status, so a callback kept from an earlier render cannot send. It is early feedback only; the service guard below is what makes it correct.
- Every store save is compare-and-set against what the page showed. The page freezes, per profile, the status values a store save may overwrite (stored models, actual resolved models, routing including the effective on/off switch, conversation spare models) when it first sees the profile, and sends them as `expected` for each profile and field it writes. A profile discovered after the page loaded is frozen when it first appears, so editing it saves normally instead of being dropped. If the service refuses, the page shows "다른 곳에서 변경됨 — 다시 불러오세요" with the profile and value, and blocks saving until a reload; nothing was written.
- A confirmed save reloads the page by itself only when the request bodies it actually applied carried every unsaved edit: a field counts as saved when every target the request wrote it to received the drafted value, and at least one did (the default profile also counts when the loaded profile received it). Otherwise the page says so and keeps the edits. For example, a default profile kept per target by an automatic-mode target, or a slot model left out of a model-only save after slots became read-only, stays unsaved.

## Conversation spare models moved into the model section

The main conversation's spare models (native `fallback_providers`) now sit under 대화 모델 as **대화 예비 모델**. Its own target list, consent behaviour, save button and `/fallback-preview` path are unchanged, and the whole-page save still includes it.

## Removed from the page

- the "작업·검증 라우팅 폴백" card (`routing.fallback`, used only by the retired routed-job runner),
- the "기본 위임 방식의 예비 모델" card (`delegation.fallback_providers`, meaningful only for Hermes' own `default` delegation),
- the "다른 작업 방식의 예비 모델 · 고급" wrapper and the whole "예비 모델(폴백) 설정" section,
- the "기본 위임 모델 사용" (`default`) option of 작업을 맡기는 방식.

Stored values are preserved: the page never sends `routing_fallback` or `delegation_fallback` updates any more (single saves, the whole-page save and target copies alike), and it no longer sends the stored `routing.fallback` back inside `/preview` bodies either. It still reads their status. The service still refuses a model change that would collide with a stored routed-job spare model; the whole-page save explains that case before sending. The Python support for these values is unchanged, so older pages and other versions keep working.

A profile still stored on Hermes' `default` delegation (or on any method the page does not offer) is shown with that value and a note, and is never switched silently. The value is listed in the method picker only as the disabled current value; a pick of it is ignored, and "저장된 방식으로 되돌리기" returns the draft to it. Switching it is intended, but only as an explicit choice for the loaded profile: load that profile, pick a plugin method in its own picker and save. That is the only way it changes. Nothing switches it silently (loading, reloading, a save of another section or an apply never does), and a copy never switches another profile: a model-section copy skips a target stored on such a method by name, and that target receives the models only.

## Service changes

- `delegation-preview`: an update may leave out the spare policy (`policy`/`slot_policy` together with `allow_additional_cost`), `profile_routes`, or both; with both left out it is an explicit method-only change. A left-out part is kept exactly as stored, and an absent key stays absent; nothing is fabricated. `allow_profile_access` must be `false` when `profile_routes` is left out. Submitted `profile_routes` are authorized again at apply even when unchanged; only routes left out keep the stored list without re-validation, so a stored entry for a deleted profile does not block a method change.
- `preview`: `routing.fallback` may be left out in every scope; the stored value is then kept. A body that includes it must send the stored value unchanged in every scope (whole page, models, routing, timeouts); this endpoint never writes it. For a profile without a stored entry it is compared with the initial (disabled) value, without resolving the profile's models, so an older client's timeout-only save cannot fail on an unrelated model.
- `delegation-preview` consent: a literal `allow_profile_access: true` is required only when submitted routes add a profile or set the default to a different non-null profile (`new_profile_authority`). Descriptions, removals, a cleared default and an unchanged stored default re-written with the block are accepted without it.
- `preview` and `fallback-preview`: optional `expected`, a list of `{profile, models?, actual_models?, routing?, native_fallback?}` holding the values the page showed. When present it must cover every profile and field the request writes (model targets: `models` and `actual_models`; routing and its on/off: `routing`; conversation fallback: `native_fallback`), and preview and apply compare each value with the current one and refuse the whole save on any difference, before the first write. The refusal is `ExternalChange`, reported by the CLI bridge as `{"error": "ExternalChange", "conflict": {"profile", "field"}}` (for example `conflict: {profile: "claire", field: "actual_models.main"}`). The follow-up store write of a combined model-section save carries the same frozen values; the delegation-method write before it changes none of them. Clients that send no `expected` keep the previous behaviour. With `expected`, only the conversation fallback can be part of the request.
- `delegation-preview` needs no `expected`: every update already carries the per-target digest the page froze at load, which covers the method, both spare policies, the allow-list and the plugin code. It is checked at preview and again (config CAS) before the first write.
- A ticked profile-section target that disappears stays listed and blocks that save by name on every path, including after switching the loaded profile or reloading, until it is unticked.
- The same holds for every list the operator chose by hand: model-section targets, time-limit targets, conversation spare-model targets and re-enable ticks. A name a refresh no longer lists stays ticked, blocks that section's save (and the whole-page save when it would write that list) by name, and is removed only by unticking it, on every path, including switching the loaded profile and reloading. A source switch ends only the pending copy intent, never the hand-picked selection. A ticked re-enable stays an unsaved edit while its profile is missing, so another save never reloads it away, and an explicit reload keeps it listed and blocking as well (a tick on a profile that is still off keeps its tick; one switched on elsewhere is dropped).
- A default selection the page made by itself (every eligible profile for time limits and conversation spare models) stays symbolic: it follows the live eligible list, including a profile that becomes eligible later, until the operator edits the list by hand. A hand-edited list is never widened.
- `apply` refuses any store-path plan unless the canonical store file is byte-for-byte the one preview computed the plan from (a SHA-256 of the file recorded at preview, read before and after loading it). The plan replaces the whole store, so this keeps a save from reverting another profile's entry that changed without a revision bump. Profile config keys (including `skills.disabled`), conversation fallback config and time limits were already compare-and-set per key or file at apply; the store file was the only file replaced wholesale.
- A profile whose routing skill is disabled in its own `skills.disabled` stays off through every other save, even though its canonical flag is on and the page sends it in `routing_profiles`. The service removes the routing skill from `skills.disabled` only for an explicit re-enable: a profile whose canonical flag goes from off to on in the request, or one named in the new optional `reenable_profiles` list (which must be a subset of `routing_profiles` and is accepted only in the routing scope or a whole-page save). The page offers such a profile in the re-enable list and sends `reenable_profiles` only from that save, so a re-enable counts as saved only when a request names it. The preview's `skills.disabled` row now shows the routing skill's own state before and after, not the canonical flag.
- No plan creates a store entry for a profile it does not target. The standalone conversation spare-model save, the routing-scope and whole-page saves and the combined plan keep every untargeted entry exactly as stored, and an absent entry stays absent, so a profile's current models are never pinned into the store by someone else's save.
- Every entry a plan leaves unchanged is written back with exactly the keys and values it has in the file (taken from the exact bytes the plan was computed from), so a save never adds normalized fields such as `delegation_fallback: null` to another profile's entry. The store file as a whole is re-serialized (sorted keys, indentation), so its formatting may change; its content does not. Only a schema change (a migration) writes normalized entries.
- A model copy target that already matches the draft and has no store entry is verified against the approved model values after apply, so a copy mixing such a target with changed ones reports `applied`. The other final checks (routing, time limits, conversation spare models) never read store entries.
- A target receives a model-router delegation method only when task routing is effectively on for it: its canonical flag is on AND its routing skill is not disabled in its own config. With either switch off it is named in the target list, left out of the method batch, and still receives the model copy, so one such target never stops the whole copy.
- Every key a stored entry does not have stays absent when this save does not change it, on targeted entries too: a conversation spare-model or model save no longer adds `delegation_fallback: null` or `fallback_consent.delegation: null` to a schema-2 entry.
- The store digest is checked once more after the new store payload is written to its temporary file and synced, immediately before the file replace, in addition to the earlier check; a change in between refuses the apply, removes the temporary file and writes nothing.
- Apply re-checks the store file's digest immediately before replacing it, after backups and validation, and refuses with nothing written if it changed in between.
- The routing expectation includes `skill_enabled`, the routing skill's state in the profile's own `skills.disabled` (`null` when unreadable), next to the canonical flag. A routing save therefore cannot switch a profile back on that was switched off in its config after the page loaded.
- `expected` is strict: an explicit `null` is refused (only an absent key keeps the legacy behaviour); every value has the exact status-row schema (real booleans, strings of at most 512 characters, no unknown keys, bounded chains and slots); and there is at most one entry per discovered profile, so the bound always fits every profile a status can report. Extra entries only add checks and never make a profile a target.
- The frozen values are compared before anything else is computed, so a change elsewhere that leaves a model unresolvable is reported as that profile's `ExternalChange` (for example `actual_models.main`), not as a generic resolution error.
- A cross-language contract test keeps the page and the writer in step: `tests/test_native_contract_desktop.mjs` generates the page's `/delegation-preview` bodies into `tests/fixtures/native_delegation_contract.json` (failing when it is stale), and `tests/test_native_contract.py` applies each one to a temporary config and checks the stored keys. The same Node test writes `tests/fixtures/page_expectation_contract.json` (the page's `expected` mapping of a status row), and `tests/test_page_expectations.py` checks that this mapping of the service's own status rows is exactly what the service compares.

## Known limits

- A page status read is limited to 64 pages (`STATUS_PAGE_LIMIT`; each page is bounded at about 30,000 characters by the service). A status that needs a 65th page fails with the "settings changed" message. This predates v0.12.0.

## Status line

- A child resumed with delegate_task action=continue now gets its own status-line row that inherits the original request (kind/slot), instead of an unknown-kind row; the original row keeps its own counts.
- When a continuation restarts a child before an earlier run's stop was observed (grouped batch stops wait for siblings), unsettled earlier runs and held stops carry over across further continuations. A stop is attributed to an earlier run only on evidence: it arrived before the latest restart, its duration exceeds the current run's age, or the current run was active (tool or API hook, including a usage report) after it. Outcomes are assigned only when the evidence is unambiguous or all candidate stops share one outcome; otherwise the runs end with an unknown outcome (`ended`, shown as unknown unless the native roster reports the run), never as still running.

## Known limits (status line)

- More than 16 unsettled earlier runs of one continued child lose stop accounting for the oldest ones.
- A replayed older `running` event can show an `ended` (unknown) continuation row as running again until a terminal event arrives.

## Delegation guidance

When a task slot runs on Main's own model, delegate only for context weight, long runtime or at least two independent workstreams. Design stays with Main, and short screen actions stay in Main. An independent or final review remains a fresh child.

## Other wording

Summaries, labels and section descriptions no longer refer to the removed cards; the conversation spare-model card, its errors and preview labels say "대화 예비 모델".
