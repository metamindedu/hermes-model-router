# v0.16.1: The status line names the advisor child

## Fixed: an ask_advisor child showed as "종류 미확인"

Reported case: during an `ask_advisor` call the status line above the composer showed the advisor child as `종류 미확인 · gpt-6.2-astra`, with `요청: 실행 종류 미확인`. The plugin's execution roster creates its rows from the model-facing `delegate_task` call. `ask_advisor` dispatches its child directly, so no row existed, and the Desktop showed only the bare native child, which it never labels by guessing.

What changed (`model_router/execution_roster.py`):

- `pre_tool_call` for `ask_advisor` creates one row for the call: model, Heavy, purpose and slot `advise`, one child. As with every row, no question, context or answer text is kept.
- `subagent_start` binds that row to the child whose goal starts with the advisor marker (`Advisor consultation <nonce>.`), and only if exactly one advisor row of that parent session is waiting. With several waiting (parallel calls from one turn) nothing is bound; the roster never guesses.
- The row learns the call's delegation id from the core's live registry (`tools.delegate_tool_registry.get_subagent_attribution`), on a status-line read, outside the roster lock, and only if the registry's goal is an advisor goal. The Desktop then matches the row to the native child by subagent id and delegation id, as for any delegation, and shows `조언` with the child's model, tool and time.
- `post_tool_call` for `ask_advisor` settles a row the child's own stop has not settled: an interrupted, cancelled or timed-out call keeps that outcome, `ok` is completed, anything else an error. A refusal after the child ran (its answer was discarded) is an error in the roster even if the child completed; the Desktop may then show `상태 미확인` because the native completion event disagrees. A child's own interrupted, cancelled or timed-out outcome is kept. A `skipped` call (the slot runs on the asker's model) removes its row, because no child ran.
- A waiting advisor row whose call never returned stops counting for binding after 420 seconds (the host's default tool deadline), so a lost hook cannot keep later calls unbound. That row itself stays shown as waiting until it is evicted, and in the rare case that its own child starts later while another call waits, the child can be shown on the other call's row.

## Limits

- Parallel `ask_advisor` calls from one turn keep showing their children as `종류 미확인`, with a `조언` request row each.
- Between the child's start and the core registering it (a moment), a status-line read can show the row as `조언 · 상태 미확인` next to an unknown native row; the next refresh (at most 5 seconds) merges them.
- Binding is by the advisor goal marker. A model-facing `delegate_task` that forges that marker while an advisor call waits could take its row; that child is read-only under the guard anyway.
- Verified with unit tests and with the real core registry in the offline native test. The Desktop line itself was not re-checked in a running app.
